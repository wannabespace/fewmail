# Architecture

| Topic | Rule |
| --- | --- |
| Layout | `apps/api` (Bun + Hono), `apps/web` (Vite SPA, React 19, TanStack Router + Query), `packages/db` (Drizzle + Postgres), `packages/shared` (enums and helpers shared by both), `packages/ui` (the kit). |
| Services | `apps/api/services/*` own all behaviour and take `userId` first. `orpc/router.ts` (web), `mcp.ts` (MCP over Streamable HTTP, OAuth), `telegram.ts` (grammY) and `whatsapp.ts` (Cloud API over plain `fetch`) only adapt them. Errors a user can cause throw `NotFoundError`, mapped per surface. |
| Error handling | No `try` / `catch` anywhere (API, web, packages): wrap the call in `better-result` — `Result.try` (sync) or `Result.tryPromise` (async) — and branch on `isOk()` / `isErr()`, or `unwrapOr(fallback)` when a fallback is the whole policy. A thrown error arrives wrapped in `UnhandledException`: log, `instanceof`-check or rethrow `result.error.cause`, never `result.error`. A thunk loses narrowing of properties checked outside it (`device.keys`, `mailbox.historyId`): copy them into a local first. Promise `.catch()` on fire-and-forget work stays (`logErrorAs`). `apps/web/public/sw.js` is the one exception — the service worker imports nothing. |
| API layer | oRPC with arktype input schemas. The web imports the `Router` type from `@fewmail/api/router`; outputs typed via `RouterOutputs`. The API package uses relative imports (no `~/` alias) because the web type-checks it. Requests made in one tick travel as one HTTP request (`BatchLinkPlugin` in streaming mode ↔ `BatchHandlerPlugin`; `live` is never batched), CORS preflights are cached for a day (`maxAge`) and API responses are compressed (`hono/compress`) — every round trip shows in the UI. |
| Auth | Better Auth, Google only, with the `gmail.modify`, `calendar.events`, `contacts.readonly` and `contacts.other.readonly` scopes (contacts only for senders' photos: `lib/contact-photos.ts` lists each mailbox's contacts and other contacts through the People API, cached per user for 6 hours, a 403 meaning no photos; `me.hasContacts` false shows a dismissible notice to sign in again), `accessType: offline` and `prompt: consent` (no refresh token otherwise). OAuth tokens are encrypted by Better Auth. Sessions are cached in a signed cookie for 5 minutes (`session.cookieCache`), so a revoked session lives up to that long and most RPCs skip the session lookup in Postgres. Gmail access tokens come from `auth.api.getAccessToken` with the user's Google account row id, cached in memory per user until a minute before expiry and dropped when Better Auth updates the account (a new sign-in). **Added mailboxes** (`services/mailboxes.ts`, Settings → Mailboxes) consent through our own Google OAuth (`mailboxConsentUrl`, callback `GET /mailboxes/callback`, redirect URI registered in Google Cloud), never Better Auth's `linkSocial`: their grant lives on the `mailboxes` row (`googleAccountId` searchable, `refreshToken` encrypted) and never becomes an `accounts` row, because Google sign-in finds the user by account and whoever owns an added mailbox would be signed in to this user. The callback requires the browser's own session to match the consent's user, so a consent link sent to someone else adds nothing. Removing one does not revoke the grant (it is shared with that account's own Fewmail, if any). |
| Gmail | Plain REST in `lib/gmail.ts` (no googleapis SDK); every call takes a `GmailAccount` (a mailbox row: no `refreshToken` = the sign-in mailbox through Better Auth). A user has one sign-in mailbox (`googleAccountId` null, created by `ensureMailbox`) plus any added ones; everything above the mailbox (Home, queue, rules) is per user and merges them. Thread changes go to the thread's mailbox (`mailboxOfThread`), replies and forwards leave from the original's mailbox, new mail from `mailboxId` or the sign-in one (`outbox.mailboxId`), search asks every mailbox, or the one Mail is narrowed to (`searchMailboxes`); found mail Fewmail holds is listed from the database, the rest is read live (`readOlderMessages`) and never stored. **Held mail**: `mailboxes.heldSince` is where the database's mail of a mailbox begins — everything received since is in `messages`. The worker moves it back a week per tick (`holdEarlierMail`, `in:anywhere`, html left null and fetched on first open) to `HELD_MONTHS` (3) before the mailbox was added; that mail is stored for reading only, never passed to `processIncoming` and never analysed (the Mail list groups it under Earlier). `listMail`'s first page is held mail only (bounded by `heldSince`, so the refetch every live event triggers never reaches Gmail); a page asked with `before` goes on past `heldSince` straight from Gmail (`services/older-mail.ts`: `messages.list`, never `threads.list`, which orders by a thread's newest email and so let one reply to an old thread skip every thread between, + metadata-only `threads.get` per thread, cached in API memory for a minute per user and dropped on any label change through `changeThreadLabels`) for Inbox, Unread, Pinned, Archive, Spam and Trash. **No page may skip mail**: the web asks the next page after its oldest row and ends a list on an empty one, so each source reports a `floor` (held: its oldest row on a full page; a mailbox read live: its last email's date while Gmail has more), the merged page keeps only rows from the highest floor on, a mailbox read live reads up to four Gmail pages before answering with no row, `before:` is rounded up a second (our filter is in milliseconds) and a failed mailbox fails the whole page (the web shows Try again) instead of answering empty. The inbox header shows Gmail's own conversation count (`mail.inGmail`, `labels.get INBOX` `threadsTotal` per mailbox, 1 quota unit each); the analysis-based filters and Snoozed have no older pages. A live row's id is a version-8 UUID (`liveMessageId`: mailbox prefix + Gmail id), so every procedure taking a message id takes it: `ownMessage` (`services/stored-mail.ts`) stores its whole thread first, and `getThread` stores a thread it does not hold (`holdThread`) — opening, a hover's prefetch and any action are what store older mail. A live page costs ~500 Gmail quota units (the per-user limit is 250/s): the web reads one list's older page at a time, only when it is scrolled. Sync: first run takes `in:inbox newer_than:3d` (60) plus recent sent mail for voice, and the sign-in mailbox's first run also starts Reading's first week in the background (`writeFirstIssues`: `unsubscribe newer_than:8d`, 100, stored and judged by Jev alone through `recordNewsletter`, which keeps only a newsletter's analysis); later runs use the History API from `mailboxes.historyId`, falling back to a full first run when history expired (404). A new incoming email whose thread Fewmail holds no other message of gets the rest of its thread fetched (`completeThreads`), stored for reading and context only — never passed to `processIncoming`. `syncMailbox` claims the mailbox atomically (`mailboxes.syncStartedAt`, taken over after 15 min) because the API and the worker both sync; `historyId` and `lastSyncedAt` are written only after `processIncoming`, so `null` means the first read is still running (Home shows it). A failed run (any Gmail error but a 404 on a vanished message, or a throw in `processIncoming`) keeps its `historyId` and deletes the messages it stored (`forget`), so the next run stores and processes them again instead of skipping them as known. Search goes through Gmail's own search (`q`), since subjects and bodies are encrypted in our DB. **Attachments**: `parseMessage` keeps each file part's name, type, size, Gmail `partId` and `Content-ID` in `messages.attachments` (`MailAttachment`, encrypted; named files and the nameless images an HTML body draws by `cid:`); mail stored before the column is read again on first open (`fillFromGmail`, which also rewrites `html` and `code`). The bytes are never stored: `GET /attachments/:messageId/:partId` (`readAttachment`, session cookie, 404 for anything not the user's) reads the part from Gmail by its `partId` (Gmail's attachment ids change on every read), serving PDFs and raster images inline and everything else as a download (`application/octet-stream`, `nosniff`), since the sender names the type and HTML or SVG must never render on our origin. The reader swaps an HTML body's `cid:` images for that URL (`cidSource`) and lists the other files under the email (`listedAttachments`); the agent's `read_thread` returns the same list. |
| Worker | Separate process and Railway service (`worker.ts`; `pnpm dev` runs it as `dev:worker`), one tick a minute: sync mailboxes older than 2 minutes (and create the mailbox for anyone with settings but none), send the morning messages at `briefHour` in the user's time zone (for every user: yesterday's Reading issue is written (`writeReadingIssue`, the only time its summary is written) and sent to Telegram and WhatsApp, or as a device notification without them; Monday's weekly report only where a messenger is connected; `user_settings.morningSentAt` is set before sending, so a failure is not retried that day and a missed day's issue is never written later), push importance-3 actions to devices and — with the agent — to each messenger whose link keeps `urgentPush` on (`urgentPushTargets`; Settings → Notifications switches it per messenger), once (`actions.notifiedAt`, set even when a channel fails; each channel fails alone), turn due commitments into actions (`processDueCommitments`), offer the weekly cleanup (`offerCleanup`, looked at once a week via `user_settings.cleanupCheckedAt`), learn the user's writing style (`learnDueVoices` → `learnVoice` in `services/sent-mail.ts`: right after the first sync, then once `VOICE_EVERY_SENT` more sent emails arrived, at most once a day; the fast model describes greetings, sign-offs, formality, length and habits from the last `VOICE_SAMPLE` sent emails into `user_settings.voice`, style only, never content; `voiceLearnedAt` is set before the call, so a user without budget or sent mail waits for the next sent emails). Agent-only steps pick their users with `hasAgentSql`, not `getPlanInfo` per user. A per-key in-memory lock prevents overlap, which is why the worker runs as exactly one replica (see `monorepo.md` → Deploy); the API may scale. The API still dispatches its own outbox timers for exact Undo Send timing; the worker's sweep is the safety net and the atomic claim keeps them from both sending. Telegram and WhatsApp: the API owns the webhooks / polling, the worker only sends. |
| AI | Per email, **Jev** (TypeSafe through OpenRouter's decisions endpoint as `~typesafe/jev-latest`, `lib/jev.ts`, `services/classify.ts`) makes every typed decision in one call — category, importance score, needs-reply, suggested action (stored as `analyses.suggestedAction`; a noise one no rule covers waits in Home's Tidy, and one Jev gives under 0.7 odds for noise as a whole is dropped), matching rule — and the LLM only writes text (summary, reason, action title, extracted facts; the approve button names the action kind in the interface language, never the stored title) for mail that is not noise; when the Jev call fails the LLM does both. `services/agent.ts` `analyze`: Free gets Jev-only analysis (summary = snippet, no LLM) and only rules with a Gmail effect are offered to Jev; Pro/trial also get LLM text. Network facts (`withNetworkFacts`: risk → importance 3, suspicion and bulk → ≤ 1, no reply) adjust Jev's decisions before noise and the allowance are judged; when the text call fails the email keeps a Jev-only analysis and is not counted. The LLM-only fallback offers the same actions as Jev (`SUGGESTED_ACTIONS` from `ACTION_CRITERIA` in `classify.ts`, whose criteria also write its prompt). OpenRouter through the AI SDK (`lib/ai.ts`): `models.fast` (TypeSafe Jev Router `typesafe/jev-router`, which picks the model per request — only providers with `data_collection: 'deny'`; Gemini Flash fallback) analyses every message with structured output; `models.writer` (Claude Sonnet) writes drafts. **Every** `generateText` / `streamText` passes `telemetry: trackUsage(userId, feature)` (`lib/ai.ts`): each model call (every step of an agent request too) becomes an `ai_usage` row — feature, model, input / output / cache tokens and `cost`, the USD OpenRouter billed for it (`providerMetadata.openrouter.usage.cost`, null when absent). A new AI call adds its feature to `AiFeature` (`packages/db/schema/settings.ts`). Jev and the Codestral FIM in autocomplete are not tracked. **The thread is the unit**: `analyzePending` judges only the emails this sync inserted (an insert returns its row to one sync only, so parallel mailbox syncs never judge an email twice; history and context mail is never judged) and of those only an incoming email that is its thread's latest — a later reply of the user's own makes it answered — and never one from another of the user's own mailboxes (Gmail marks it SENT only where it was sent). Analysis and drafts see up to four earlier emails of the thread (`threadPrompt`), drafts write in the user's learned style (`user_settings.voice`, also given to autocomplete) with their last `SENT_EXAMPLES` sent emails for tone and sign-off, know the user by their mailbox addresses (the sender is someone else even when the names match), sign with the user's name in the reply's script, use a knowledge fact only when the email is about it and never pick between options the email asks the user to choose from, and a newer email in the thread — incoming or the user's own — dismisses the pending per-email cards of older emails (`retireStaleActions` compares dates, since a first sync stores old sent mail too), and an email whose thread already holds a newer one queues no card, so an analysis that finishes late cannot bring a stale card back. Mail lists one row per thread (its latest matching email, unread if any email is, with `threadSize`); unread counts count threads. The user's own sent mail is left out of lists and counts unless Gmail put it in the inbox (mail to themselves, `isReceived`). Prompts never let the model invent facts; drafts contain no placeholders. **Card links**: a `pay` or `read` card of an agent plan gets `payload.link` from `pickLink` (`card_link`): the fast model sees the subject, the summary and the email's links (`emailLinks`, at most `LINK_LIMIT`, each as its text and host) and answers a number and a purpose, never a URL, so it cannot hand out an address the email does not hold; no link for mail with `risk` or `suspicion`. `extracted.meetingStart` (`yyyy-MM-ddTHH:mm` in the user's time zone) becomes a `schedule` or `reply` card's `payload.event`. |
| Database | Drizzle (`packages/db`), uuid v7 ids, `snake_case` tables, **No user data in clear text** (`packages/db/utils.ts`, AES-GCM, `ENCRYPTION_SECRET`): `encryptedText` / `encryptedJson` (random IV) for anything only read back; `searchableText` / `searchableTextArray` (deterministic, HMAC-derived IV) only for columns used in `eq`, `inArray`, `arrayContains`, unique indexes or `groupBy` — addresses, `messages.fromDomain`, Telegram chat ids, WhatsApp phone numbers, Google account ids. Array columns are filtered with `arrayContains` (`@>`), never `= ANY`, so the GIN indexes on `messages.label_ids`, `to` and `cc` are used. Encrypted columns cannot be sorted, `LIKE`d or `split_part`ed in SQL: sort in JS, add a searchable column for the part you need, and give aggregates `.mapWith(column)` so they decrypt. Plain columns hold only ids, dates, flags, enums, amounts, Gmail ids/labels, keyed hashes and public lists. Any new text column from a user or their mail is encrypted. Agent tables (`commitments`, `people`, `unsubscribes`, `bulk_prints`, `domain_sightings`, `payment_details`) live in `packages/db/schema/insight.ts`. Migrations: `pnpm db:generate` then `pnpm db:migrate`. |
| Integrations | **One bot, two transports**: `services/messenger.ts` is everything Telegram and WhatsApp do — `press` (buttons and commands: `a:` approve, `all:<kind>:<shown>` approve every card of a kind the queue showed (`shown` is a keyed hash of those cards' ids and drafts, so a card that arrived, left or was redrafted since makes it refuse and show the queue again; each send gets its own message with its Undo), `u:` undo (a send already gone answers `t.errors.alreadySent`), `d:` skip, `r:` shorter, `w:` write a follow-up's reminder, `e:` edit, `queue`, `reading` the latest Reading issue, `week` the weekly report), `follow` (typed or transcribed text, edit mode first; a `/skill`, like `queue`, leaves edit mode and runs), `hear` (checks the message limit before paying for transcription), the replies (`itemReply`, `readingReply`, `weekReply`, `runReply`, `helpReply`) as `{ text, buttons, actionId }` built through the channel's `bold` / `italic` / `plain` / `link` (Telegram `<a>`, link previews off; WhatsApp the URL on its own line), and `failureText` (user's language when linked). `telegram.ts` / `whatsapp.ts` keep only transport (HTML + inline keyboard / signature, button clipping, 24 h template). Drafts show at most 3 500 characters, with a note when cut, since Send sends the whole draft; longer messages are split at line breaks. `bot_messages` (keys searchable) is shared by the API and the worker: sent message → its action (a reply to it targets that draft), a chat's edit mode (expires after 30 min), a chat's last question and answer (`exchange`, encrypted, read for 30 min: `followMessage` passes it to `understand` and `askMail`, so "when did it arrive?" searches for what the previous answer was about) and handled WhatsApp inbound ids; rows older than 30 days are pruned on write. A link code only links a chat or phone when none is linked yet (or the same one) — switching means Disconnect first: a chat or phone another account holds is refused (`telegram.chatTaken` / `whatsapp.phoneTaken`), never moved, and WhatsApp reads a link code before routing a linked phone's message to its agent. Telegram: deep link `t.me/<bot>?start=<linkCode>` links a chat; inline buttons approve/skip/redraft; webhook when `TELEGRAM_WEBHOOK_SECRET` is set, long polling otherwise. MCP: the user pastes one URL (`<API_URL>/mcp`) and the client signs in through OAuth — Better Auth's `@better-auth/oauth-provider` (+ `jwt`, its `/token` disabled) with open dynamic client registration, `loginPage` `/login`, `consentPage` `/connect` (web). `/.well-known/oauth-protected-resource/mcp` and `/.well-known/oauth-authorization-server/auth` are served by `index.ts`; `mcp.ts` verifies the JWT access token (audience = the MCP URL) and also requires the user's `oauth_consents` row for that client, so Settings → Disconnect (`disconnectApp`) cuts a client off at once though its JWT lives an hour. Tools mirror the services; a `consent` tool never runs through MCP, whatever the client allows: `proposeConsent` (`services/agent-run.ts`) stores the call as a pending `consent` card with the reads it needs (the thread, Home or events), and the same tool with the same input while that card waits reuses it, so a retrying client never makes a second yes; `deliverHomeLink` (`home-link.ts`) sends Home's link as a push and to Telegram and WhatsApp, each channel failing alone and never failing the call once the card exists; the client gets `waiting_for_approval`, and the yes on Home runs it; `get_person` mirrors people. Telegram also takes free text and voice messages (`services/instructions.ts` `followMessage`): the fast model reads each as a reply to draft, a question answered by `askMail` (texted: a few sentences without `[n]` or ids, then a `link` to each email the user asked to see, `WEB_URL/mail/$threadId`), or neither (the bot answers with what it can do, as do `/help` and `/start` once linked); audio goes to Mistral `voxtral-mini-latest` for transcription and is not stored; replying to a bot message targets its thread. The webhook uses `onTimeout: 'return'`: drafts outlast grammY's 10 s, and a timed-out update makes Telegram retry it and hold every later one. Handler errors reply `somethingWrong` (or `t.limits.messages`) instead of going silent; a button press is answered exactly once — Telegram throws on a second answer. WhatsApp (`whatsapp.ts`, Cloud API): the settings link opens `wa.me/<WHATSAPP_NUMBER>` with a prefilled `Fewmail <linkCode>` that links the sender's phone; `GET /whatsapp` answers Meta's verify-token check, `POST /whatsapp` checks `X-Hub-Signature-256` with `WHATSAPP_APP_SECRET`, answers 200 at once and handles messages after (Meta redelivers, so seen message ids are skipped). Same commands as Telegram as reply buttons (max 3, titles ≤ 20 chars, body ≤ 1024 — longer text goes first as its own message); free text and voice notes go through the same `followMessage`, replying to a bot message targets its draft. Meta allows free-form messages only within 24 h of the user's last message (`whatsapp_links.lastInboundAt`); outside it the newsletter digest, the weekly report, schedule runs and urgent pushes go out as the approved `WHATSAPP_TEMPLATE` (one body variable with a one-line preview, one Quick Reply button whose payload `reading` / `week` / `queue` / `chat:<id>` (a schedule run) sends the full content once tapped). |
| Notifications | `services/notifications.ts`: `notify(userId, notification)` buffers per user and delivers after `BATCH_MS` (10 s) — whatever arrives in that window goes out as one combined notification. In-memory, so it runs in the worker only and the worker flushes it on SIGTERM. Targets are `devices` (one row per browser / app, `kind` from `DEVICE_KINDS`, `token` searchable, `keys` encrypted); each kind has its own sender — `web` is Web Push (`web-push`, VAPID keys `VAPID_PUBLIC_KEY` / `VAPID_PRIVATE_KEY`, 404/410 deletes the row). Mobile and desktop apps join as a new kind plus a sender, nothing else changes. Web: `public/sw.js` shows the push and opens its `url` (navigating an open tab, or a new window when that tab is not controlled by the worker); `lib/push.ts` registers it, Settings → Notifications toggles it on every plan, sign-out removes it. Payloads are end-to-end encrypted to the browser, but they carry sender, subject and summary — the privacy policy says so. |
| Client state | TanStack Query via `orpc.*.queryOptions()`; optimistic removal from the queue on approve/skip. No global stores. `gcTime` is a day and nothing keeps previous data by default (opt in per query, e.g. search): a query keyed by an id must never show another id's data. `me` lives in the query cache — `/_app`'s `beforeLoad` answers from it on every navigation, `useMe()` reads it and `useSaveSettings()` writes settings into it before the server answers. Every `/_app/*` route has a `loader` that warms its queries through `warmQuery` (`lib/query-client.ts`: cached data renders at once and refreshes behind it, only data never loaded holds the navigation), so `defaultPreload: 'intent'` fetches a page's data on hover; the calendar's loader never awaits Google and also warms the previous and next range. Mutations write their result into the cache in `onMutate` and refetch the narrowest key in `onSettled` (the refetch is the rollback); a bare `invalidateQueries()` is only for a reconnect — anything else names its keys or calls `refetchChanged(topics)` (`lib/orpc.ts`), the same path live events take. Mail is TanStack DB (`apps/web/src/lib/mail-db.ts`, in memory, never persisted): `mailRowsOf(mailboxId)` holds every list of a mailbox at once (preloaded in `/_app`, tabs are live queries), `threads` is an on-demand collection whose entries `prefetchThread` fills ahead of the click (first rows, the cursor's neighbours, hover). `listMail` keeps a thread's newest matching message by excluding any newer matching one (`notExists`), so a page walks `messages_user_received_idx` instead of sorting the mailbox. Mail actions take the thread out of every list before the server answers (`hideThread`, `showThreadRead`) and refetch once the answers settle, on error too (`refetchChanged`, so a burst's first answer never puts the rest back for a moment). Their query keys sit under `orpc.mail.key()` with an object as their second part (`{ mailboxId }`, `{ threadId }`: the key's `{}` never matches a string or null there), so mail invalidations and the live stream refresh them. Search and drafts stay plain queries (Gmail answers them live). |
| i18n | `packages/shared/i18n`: `locales.ts` (supported `LOCALES`, `matchLocale`, typed `plural` whose forms are `(n) => string`, and `Rich<Slot>` for messages with nodes inside such as links), `messages/en.ts` is the source of truth and `Messages = typeof en`; every other locale is `: Messages`, so a missing or mistyped key fails the type check. **No string placeholders**: anything with a parameter is a function, anything with a link or node is `Rich`. Adding a string means adding it to every locale in the same task. Web: `useT()`, `useDates()`, `localeStore` (`apps/web/src/lib/i18n.ts`), `getT()` outside React; only English is in the main bundle, every other locale is a chunk loaded when picked (`main.tsx` waits for the stored one), so the web never imports `messages` from `@fewmail/shared/i18n` — that pulls all of them back in; API/Telegram: `messages[settings.language]`. Right-to-left languages are not supported yet (layout uses physical `ml-`/`pl-`). |
| Marketing & SEO | Public site under `routes/_site*` (`SiteHeader`/`SiteFooter`, `components/site.tsx`; demos in `components/landing-demos.tsx`): `/` landing, `/pricing`, `/compare`, `/compare/$slug`, `/ai-email-assistant` (the page for the "AI email assistant" search: `t.site.assistantPage`, its own FAQ as `FAQPage` JSON-LD, linked from the footer) and `/mcp` (how to connect Claude, ChatGPT, Claude Code and Cursor; where directory listings point). Copy is translated like the app: `t.site` in the messages (`useT()`), in the browser's language (`localeStore`) until the visitor picks another in the footer's `LanguageSelect`; the legal documents stay English. `apps/web/src/lib/marketing.ts` keeps only the structure (`TRIAL_DAYS`, `PLANS`, `COMPARISONS` names and slugs, `COMPARISONS_CHECKED_AT`; competitor facts in `t.site.comparisons` only from their public pages). Every public page but the legal documents exists in each language: English at its path, the others under `/<locale>` (`/uk/pricing`, `/uk/` for the landing) — `LOCALIZED_PATHS`, `localizedPath`, `splitLocale` and `urlLocale` in `apps/web/src/lib/seo.ts`. The routes never see the prefix: the router's `rewrite` (`src/router.ts`) strips it on the way in and adds the current language on the way out, and stays free of side effects because `router.update` re-reads the URL. On a public page the URL sets the language (`main.tsx`, at start and on back/forward, reading the history's own location, which it notifies before writing `window.location`); picking another in the footer moves the page to that language's URL (`router.update` first, to drop the router's cached link hrefs). `localeStore` is the tab's own language, kept in memory and copied into `fewmail.locale` (localStorage, shared by every tab, so it only seeds the next visit and onboarding: the signed-in app sets the account's language in `_app.tsx`'s `beforeLoad` and another tab's footer pick never reaches it) and into the `fewmail.locale` cookie, and `apps/web/Caddyfile` redirects an unprefixed public page to the cookie's language, else to the browser's first `Accept-Language`; crawlers send neither and reach the other languages through hreflang. Titles and descriptions are `pageMeta(path, t)` from `t.site.meta`, `t.site.nav` and the comparisons. The query to rank for is "AI email": the landing's title (`meta.tagline`), description (`meta.home`), hero lead, footer tagline, the `/compare` title (`meta.compareTitle`), `/ai-email-assistant` and the first FAQ answer (also `FAQPage` JSON-LD) say "AI email agent" / "AI email assistant" in every locale (KI, IA, yapay zekâ where the language says so); a copy edit keeps the phrase. `/` sends a returning user to `/home` (or `/agent`) from `signedInStore` (localStorage, set by `/_app`'s `beforeLoad`, cleared on sign-out), so the landing never waits on the API. The `fewmail-seo` plugin in `vite.config.ts` derives `robots.txt`, `sitemap.xml` (every language with its `xhtml:link` alternates), `llms.txt` (English), `site.webmanifest`, shared OG tags and one `<url>/index.html` per page and language (`/` is `index.html` itself) with `<html lang>`, canonical, hreflang alternates (`x-default` = English), JSON-LD (`structuredData` in `seo.ts`: `WebSite` on the landing is what makes Google show "Fewmail" instead of the domain) and its body prerendered in that language (`src/prerender.tsx`, one page at a time since the language lives in global stores, through Vite's SSR loader under happy-dom, since the app reads browser globals as it imports). So a public page must render without the API, and nothing it renders may depend on the browser beyond what happy-dom fakes; `main.tsx` loads the route before replacing the prerendered HTML, and an inline script drops the landing before it paints for a signed-in visitor. The `noindex` app shell is `app.html`; `apps/web/Caddyfile` serves it for every path without its own `index.html`. A new public page is a path in `LOCALIZED_PATHS` (and in the Caddyfile's language redirects) with its title and description in `pageMeta` and `t.site.meta` in every locale, or an English-only entry like the legal ones; a new comparison is one entry in `COMPARISONS` plus its `t.site.comparisons` copy in every locale. |
