# Architecture

| Topic | Rule |
| --- | --- |
| Layout | `apps/api` (Bun + Hono), `apps/web` (Vite SPA, React 19, TanStack Router + Query), `packages/db` (Drizzle + Postgres), `packages/shared` (enums and helpers shared by both), `packages/ui` (the kit). |
| Services | `apps/api/services/*` own all behaviour and take `userId` first. `orpc/router.ts` (web), `mcp.ts` (MCP over Streamable HTTP, OAuth), `telegram.ts` (grammY) and `whatsapp.ts` (Cloud API over plain `fetch`) only adapt them. Errors a user can cause throw `NotFoundError`, mapped per surface. |
| Error handling | No `try` / `catch` anywhere (API, web, packages): wrap the call in `better-result` — `Result.try` (sync) or `Result.tryPromise` (async) — and branch on `isOk()` / `isErr()`, or `unwrapOr(fallback)` when a fallback is the whole policy. A thrown error arrives wrapped in `UnhandledException`: log, `instanceof`-check or rethrow `result.error.cause`, never `result.error`. A thunk loses narrowing of properties checked outside it (`device.keys`, `mailbox.historyId`): copy them into a local first. Promise `.catch()` on fire-and-forget work stays (`logErrorAs`). `apps/web/public/sw.js` is the one exception — the service worker imports nothing. |
| API layer | oRPC with arktype input schemas. The web imports the `Router` type from `@fewmail/api/router`; outputs typed via `RouterOutputs`. The API package uses relative imports (no `~/` alias) because the web type-checks it. Requests made in one tick travel as one HTTP request (`BatchLinkPlugin` in streaming mode ↔ `BatchHandlerPlugin`; `live` is never batched), CORS preflights are cached for a day (`maxAge`) and API responses are compressed (`hono/compress`) — every round trip shows in the UI. |
| Auth | Better Auth, Google only, with the `gmail.modify` and `calendar.events` scopes, `accessType: offline` and `prompt: consent` (no refresh token otherwise). OAuth tokens are encrypted by Better Auth. Sessions are cached in a signed cookie for 5 minutes (`session.cookieCache`), so a revoked session lives up to that long and most RPCs skip the session lookup in Postgres. Gmail access tokens come from `auth.api.getAccessToken` with the user's Google account row id, cached in memory per user until a minute before expiry and dropped when Better Auth updates the account (a new sign-in). **Added mailboxes** (`services/mailboxes.ts`, Settings → Mailboxes) consent through our own Google OAuth (`mailboxConsentUrl`, callback `GET /mailboxes/callback`, redirect URI registered in Google Cloud), never Better Auth's `linkSocial`: their grant lives on the `mailboxes` row (`googleAccountId` searchable, `refreshToken` encrypted) and never becomes an `accounts` row, because Google sign-in finds the user by account and whoever owns an added mailbox would be signed in to this user. The callback requires the browser's own session to match the consent's user, so a consent link sent to someone else adds nothing. Removing one does not revoke the grant (it is shared with that account's own Fewmail, if any). |
| Gmail | Plain REST in `lib/gmail.ts` (no googleapis SDK); every call takes a `GmailAccount` (a mailbox row: no `refreshToken` = the sign-in mailbox through Better Auth). A user has one sign-in mailbox (`googleAccountId` null, created by `ensureMailbox`) plus any added ones; everything above the mailbox (Home, queue, rules) is per user and merges them. Thread changes go to the thread's mailbox (`mailboxOfThread`), replies and forwards leave from the original's mailbox, new mail from `mailboxId` or the sign-in one (`outbox.mailboxId`), search asks every mailbox, or the one Mail is narrowed to (`searchMailboxes`); found mail Fewmail holds is listed from the database, the rest is read live (`readOlderMessages`) and never stored. **Held mail**: `mailboxes.heldSince` is where the database's mail of a mailbox begins — everything received since is in `messages`. The worker moves it back a week per tick (`holdEarlierMail`, `in:anywhere`, html left null and fetched on first open) to `HELD_MONTHS` (3) before the mailbox was added; that mail is stored for reading only, never passed to `processIncoming` and never analysed (the Mail list groups it under Earlier). `listMail`'s first page is held mail only (bounded by `heldSince`, so the refetch every live event triggers never reaches Gmail); a page asked with `before` goes on past `heldSince` straight from Gmail (`services/older-mail.ts`: `threads.list` + metadata-only `threads.get` per thread, cached in API memory for a minute per user and dropped on any label change through `changeThreadLabels`) for Inbox, Unread, Pinned, Archive, Spam and Trash; the analysis-based filters and Snoozed have no older pages. A live row's id is a version-8 UUID (`liveMessageId`: mailbox prefix + Gmail id), so every procedure taking a message id takes it: `ownMessage` (`services/stored-mail.ts`) stores its whole thread first, and `getThread` stores a thread it does not hold (`holdThread`) — opening, a hover's prefetch and any action are what store older mail. A live page costs ~500 Gmail quota units (the per-user limit is 250/s): the web reads one list's older page at a time, only when it is scrolled. Sync: first run takes `in:inbox newer_than:3d` (60) plus recent sent mail for voice; later runs use the History API from `mailboxes.historyId`, falling back to a full first run when history expired (404). A new incoming email whose thread Fewmail holds no other message of gets the rest of its thread fetched (`completeThreads`), stored for reading and context only — never passed to `processIncoming`. `syncMailbox` claims the mailbox atomically (`mailboxes.syncStartedAt`, taken over after 15 min) because the API and the worker both sync; `historyId` and `lastSyncedAt` are written only after `processIncoming`, so `null` means the first read is still running (Home shows it). A failed run (any Gmail error but a 404 on a vanished message, or a throw in `processIncoming`) keeps its `historyId` and deletes the messages it stored (`forget`), so the next run stores and processes them again instead of skipping them as known. Pro: each **board** reads its history once (`readBoardHistory`, `boards.historyReadAt`): up to 300 messages matching its Gmail query within its period (`newer_than:<periodDays>d`; a longer period resets `historyReadAt`, and `isUnchanged` stops a read whose description or period changed), taken from the database when held and otherwise read into memory (`readMessages`; only an email that becomes an entry is stored, `keptIdOf`), and passed only to `collectEntries` — never to `processIncoming`, so rules, spam and zombies never act on old mail and no Home card comes from it. Search goes through Gmail's own search (`q`), since subjects and bodies are encrypted in our DB. |
| Worker | Separate process and Railway service (`worker.ts`; `pnpm dev` runs it as `dev:worker`), one tick a minute: sync mailboxes older than 2 minutes (and create the mailbox for anyone with settings but none), send the morning messages at `briefHour` in the user's time zone (the newsletter digest and Monday's weekly report, each its own message, only to users with Telegram or WhatsApp connected; `user_settings.morningSentAt` is set before sending, so a failure is not retried that day), push importance-3 actions to devices and — with the agent — to both, once (`actions.notifiedAt`, set even when a channel fails; each channel fails alone), turn due commitments into actions (`processDueCommitments`), run due schedules (`runDueSchedules`), offer the weekly cleanup (`offerCleanup`, looked at once a week via `user_settings.cleanupCheckedAt`). Agent-only steps pick their users with `hasAgentSql`, not `getPlanInfo` per user. A per-key in-memory lock prevents overlap, which is why the worker runs as exactly one replica (see `monorepo.md` → Deploy); the API may scale. The API still dispatches its own outbox timers for exact Undo Send timing; the worker's sweep is the safety net and the atomic claim keeps them from both sending. Telegram and WhatsApp: the API owns the webhooks / polling, the worker only sends. |
| AI | Per email, **Jev** (TypeSafe, `lib/jev.ts`, `services/classify.ts`) makes every typed decision in one call — category, importance score, needs-reply, suggested action, matching rule — and the LLM only writes text (summary, reason, button label, extracted facts) for mail that is not noise; without `TYPESAFE_API_KEY` the LLM does both. `services/agent.ts` `analyze`: Free gets Jev-only analysis (summary = snippet, no LLM) and only rules with a Gmail effect are offered to Jev; Pro/trial also get LLM text. Network facts (`withNetworkFacts`: risk → importance 3, suspicion and bulk → ≤ 1, no reply) adjust Jev's decisions before noise and the allowance are judged; when the text call fails the email keeps a Jev-only analysis and is not counted. The LLM-only fallback offers the same actions as Jev (`SUGGESTED_ACTIONS` from `ACTION_CRITERIA` in `classify.ts`, whose criteria also write its prompt). OpenRouter through the AI SDK (`lib/ai.ts`): `models.fast` (Claude Haiku, Gemini Flash fallback) analyses every message with structured output; `models.writer` (Claude Sonnet) writes drafts. **The thread is the unit**: `analyzePending` judges only the emails this sync inserted (an insert returns its row to one sync only, so parallel mailbox syncs never judge an email twice; history and context mail is never judged) and of those only an incoming email that is its thread's latest — a later reply of the user's own makes it answered. Analysis and drafts see up to four earlier emails of the thread (`threadPrompt`), drafts sign with the user's name, and a newer email in the thread — incoming or the user's own — dismisses the pending per-email cards of older emails (`retireStaleActions` compares dates, since a first sync stores old sent mail too), and an email whose thread already holds a newer one queues no card, so an analysis that finishes late cannot bring a stale card back. Mail lists one row per thread (its latest matching email, unread if any email is, with `threadSize`); unread counts count threads. The user's own sent mail is left out of lists and counts unless Gmail put it in the inbox (mail to themselves, `isReceived`). Prompts never let the model invent facts; drafts contain no placeholders. |
| Database | Drizzle (`packages/db`), uuid v7 ids, `snake_case` tables, **No user data in clear text** (`packages/db/utils.ts`, AES-GCM, `ENCRYPTION_SECRET`): `encryptedText` / `encryptedJson` (random IV) for anything only read back; `searchableText` / `searchableTextArray` (deterministic, HMAC-derived IV) only for columns used in `eq`, `inArray`, `arrayContains`, unique indexes or `groupBy` — addresses, `messages.fromDomain`, Telegram chat ids, WhatsApp phone numbers, Google account ids. Array columns are filtered with `arrayContains` (`@>`), never `= ANY`, so the GIN indexes on `messages.label_ids`, `to` and `cc` are used. Encrypted columns cannot be sorted, `LIKE`d or `split_part`ed in SQL: sort in JS, add a searchable column for the part you need, and give aggregates `.mapWith(column)` so they decrypt. Plain columns hold only ids, dates, flags, enums, amounts, Gmail ids/labels, keyed hashes and public lists. Any new text column from a user or their mail is encrypted. Agent tables (`commitments`, `people`, `boards`, `board_entries`, `tasks`, `unsubscribes`, `bulk_prints`, `domain_sightings`, `payment_details`) live in `packages/db/schema/insight.ts`. Migrations: `pnpm db:generate` then `pnpm db:migrate`. |
| Integrations | **One bot, two transports**: `services/messenger.ts` is everything Telegram and WhatsApp do — `press` (buttons and commands: `a:` approve, `u:` undo, `d:` skip, `r:` shorter, `e:` edit, `queue`, `reading` the newsletter digest, `week` the weekly report, `chat:<id>` a schedule run's answer), `follow` (typed or transcribed text, edit mode first), `hear` (checks the message limit before paying for transcription), the replies (`itemReply`, `readingReply`, `weekReply`, `runReply`, `helpReply`) as `{ text, buttons, actionId }` built through the channel's `bold` / `italic` / `plain` / `link` (Telegram `<a>`, link previews off; WhatsApp the URL on its own line), and `failureText` (user's language when linked). `telegram.ts` / `whatsapp.ts` keep only transport (HTML + inline keyboard / signature, button clipping, 24 h template). Drafts show at most 3 500 characters, with a note when cut, since Send sends the whole draft; longer messages are split at line breaks. `bot_messages` (keys searchable) is shared by the API and the worker: sent message → its action (a reply to it targets that draft), a chat's edit mode (expires after 30 min), a chat's last question and answer (`exchange`, encrypted, read for 30 min: `followMessage` passes it to `understand` and `askMail`, so "when did it arrive?" searches for what the previous answer was about) and handled WhatsApp inbound ids; rows older than 30 days are pruned on write. A link code only links a chat or phone when none is linked yet (or the same one) — switching means Disconnect first. Telegram: deep link `t.me/<bot>?start=<linkCode>` links a chat; inline buttons approve/skip/redraft; webhook when `TELEGRAM_WEBHOOK_SECRET` is set, long polling otherwise. MCP: the user pastes one URL (`<API_URL>/mcp`) and the client signs in through OAuth — Better Auth's `@better-auth/oauth-provider` (+ `jwt`, its `/token` disabled) with open dynamic client registration, `loginPage` `/login`, `consentPage` `/connect` (web). `/.well-known/oauth-protected-resource/mcp` and `/.well-known/oauth-authorization-server/auth` are served by `index.ts`; `mcp.ts` verifies the JWT access token (audience = the MCP URL) and also requires the user's `oauth_consents` row for that client, so Settings → Disconnect (`disconnectApp`) cuts a client off at once though its JWT lives an hour. Tools mirror the services; `approve_action` sends mail, so its description tells the client to confirm with the user; `handle_thread`, `get_person`, `list_boards` / `get_board` mirror tasks, people and boards. Telegram also takes free text and voice messages (`services/instructions.ts` `followMessage`): the fast model reads each as a reply to draft, a question answered by `askMail` (texted: a few sentences without `[n]` or ids, then a `link` to each email the user asked to see, `WEB_URL/mail?thread=`), or neither (the bot answers with what it can do, as do `/help` and `/start` once linked); audio goes to Mistral `voxtral-mini-latest` for transcription and is not stored; replying to a bot message targets its thread. The webhook uses `onTimeout: 'return'`: drafts outlast grammY's 10 s, and a timed-out update makes Telegram retry it and hold every later one. Handler errors reply `somethingWrong` (or `t.limits.messages`) instead of going silent; a button press is answered exactly once — Telegram throws on a second answer. WhatsApp (`whatsapp.ts`, Cloud API): the settings link opens `wa.me/<WHATSAPP_NUMBER>` with a prefilled `Fewmail <linkCode>` that links the sender's phone; `GET /whatsapp` answers Meta's verify-token check, `POST /whatsapp` checks `X-Hub-Signature-256` with `WHATSAPP_APP_SECRET`, answers 200 at once and handles messages after (Meta redelivers, so seen message ids are skipped). Same commands as Telegram as reply buttons (max 3, titles ≤ 20 chars, body ≤ 1024 — longer text goes first as its own message); free text and voice notes go through the same `followMessage`, replying to a bot message targets its draft. Meta allows free-form messages only within 24 h of the user's last message (`whatsapp_links.lastInboundAt`); outside it the newsletter digest, the weekly report, schedule runs and urgent pushes go out as the approved `WHATSAPP_TEMPLATE` (one body variable with a one-line preview, one Quick Reply button whose payload `reading` / `week` / `queue` / `chat:<id>` (a schedule run) sends the full content once tapped). |
| Notifications | `services/notifications.ts`: `notify(userId, notification)` buffers per user and delivers after `BATCH_MS` (10 s) — whatever arrives in that window goes out as one combined notification. In-memory, so it runs in the worker only and the worker flushes it on SIGTERM. Targets are `devices` (one row per browser / app, `kind` from `DEVICE_KINDS`, `token` searchable, `keys` encrypted); each kind has its own sender — `web` is Web Push (`web-push`, VAPID keys `VAPID_PUBLIC_KEY` / `VAPID_PRIVATE_KEY`, 404/410 deletes the row). Mobile and desktop apps join as a new kind plus a sender, nothing else changes. Web: `public/sw.js` shows the push and opens its `url` (navigating an open tab, or a new window when that tab is not controlled by the worker); `lib/push.ts` registers it, Settings → Notifications toggles it on every plan, sign-out removes it. Payloads are end-to-end encrypted to the browser, but they carry sender, subject and summary — the privacy policy says so. |
| Client state | TanStack Query via `orpc.*.queryOptions()`; optimistic removal from the queue on approve/skip. No global stores. `gcTime` is a day and nothing keeps previous data by default (opt in per query, e.g. search): a query keyed by an id must never show another id's data. `me` lives in the query cache — `/_app`'s `beforeLoad` answers from it on every navigation, `useMe()` reads it and `useSaveSettings()` writes settings into it before the server answers. Every `/_app/*` route has a `loader` that warms its queries through `warmQuery` (`lib/query-client.ts`: cached data renders at once and refreshes behind it, only data never loaded holds the navigation), so `defaultPreload: 'intent'` fetches a page's data on hover; the calendar's loader never awaits Google and also warms the previous and next range. Mutations write their result into the cache in `onMutate` and refetch the narrowest key in `onSettled` (the refetch is the rollback); a bare `invalidateQueries()` is only for a reconnect — anything else names its keys or calls `refetchChanged(topics)` (`lib/orpc.ts`), the same path live events take. Mail is TanStack DB (`apps/web/src/lib/mail-db.ts`, in memory, never persisted): `mailRowsOf(mailboxId)` holds every list of a mailbox at once (preloaded in `/_app`, tabs are live queries), `threads` is an on-demand collection whose entries `prefetchThread` fills ahead of the click (first rows, the cursor's neighbours, hover). `listMail` keeps a thread's newest matching message by excluding any newer matching one (`notExists`), so a page walks `messages_user_received_idx` instead of sorting the mailbox. Mail actions take the thread out of every list before the server answers (`hideThread`, `showThreadRead`) and refetch on error. Their query keys sit under `orpc.mail.key()`, so mail invalidations and the live stream refresh them. Search and drafts stay plain queries (Gmail answers them live). |
| i18n | `packages/shared/i18n`: `locales.ts` (supported `LOCALES`, `matchLocale`, typed `plural` whose forms are `(n) => string`, and `Rich<Slot>` for messages with nodes inside such as links), `messages/en.ts` is the source of truth and `Messages = typeof en`; every other locale is `: Messages`, so a missing or mistyped key fails the type check. **No string placeholders**: anything with a parameter is a function, anything with a link or node is `Rich`. Adding a string means adding it to every locale in the same task. Web: `useT()`, `useDates()`, `localeStore` (`apps/web/src/lib/i18n.ts`); API/Telegram: `messages[settings.language]`. Right-to-left languages are not supported yet (layout uses physical `ml-`/`pl-`). |
| Marketing & SEO | Public site under `routes/_site*` (`SiteHeader`/`SiteFooter`, `components/site.tsx`; demos in `components/landing-demos.tsx`): `/` landing, `/pricing`, `/compare`, `/compare/$slug` and `/mcp` (how to connect Claude, ChatGPT, Claude Code and Cursor; where directory listings point). Copy is translated like the app: `t.site` in the messages (`useT()`), in the browser's language (`localeStore`) until the visitor picks another in the footer's `LanguageSelect`; the legal documents stay English. `apps/web/src/lib/marketing.ts` keeps only the structure (`TRIAL_DAYS`, `PLANS`, `COMPARISONS` names and slugs, `COMPARISONS_CHECKED_AT`; competitor facts in `t.site.comparisons` only from their public pages). Crawlers and link previews get English: `PUBLIC_PAGES` reads `messages.en`. `/` sends a returning user to `/home` (or `/agent`) from `signedInStore` (localStorage, set by `/_app`'s `beforeLoad`, cleared on sign-out), so the landing never waits on the API. `apps/web/src/lib/seo.ts` `PUBLIC_PAGES` is built from that data; the `fewmail-seo` plugin in `vite.config.ts` derives `robots.txt`, `sitemap.xml`, `site.webmanifest`, shared OG tags and one `<path>/index.html` per public page (`/` is `index.html` itself). The `noindex` app shell is `app.html`; `apps/web/Caddyfile` serves it for every path without its own `index.html`. A new public page is one entry in `PUBLIC_PAGES`; a new comparison is one entry in `COMPARISONS` plus its `t.site.comparisons` copy in every locale. |
| Legal & account | `/privacy` and `/terms` are public routes rendering `apps/web/src/legal/*.md`; they describe exactly what the code does (Google API Limited Use included) — a change in what data is read, stored, sent or to whom updates them and `LEGAL_UPDATED_AT` in the same task. Account deletion is Better Auth `deleteUser`: it revokes the Google grant first, then every table cascades from `users`. |
| Plans | `services/plan.ts`: `getPlanInfo` (free / trial / pro / max — an active subscription is Max when its price is one of Max's two, Pro for any other — else `trial_ends_at`), `hasAgent`. **Usage**: `usage` (one row per user and UTC month) against `PLAN_LIMITS` (`packages/shared/agent.ts`). `analyzePending` takes an `emailAllowance` and the LLM writes only while it lasts (urgent mail +10%), otherwise the email is analysed as on Free; an email is reserved before the call (`take`) and given back when the call fails (`refund`), so only written emails count; `spendMessage` counts and gates `streamChat` (new user turns only, not approval answers), the `ask` procedure and `followMessage` (Telegram, WhatsApp); `requireRoom` caps boards (`createBoard`) and active tasks (`createTask`). Over a limit services throw `LimitReachedError` (`services/limit-error.ts`) → oRPC `TOO_MANY_REQUESTS` with `{ limit, total, resetsAt }`, which the web turns into `t.limits.*` (`limitText` in `lib/orpc.ts`); the bots answer `t.limits.messages`; `me.usage` feeds the Settings meters. Split: every Jev decision is free (classification, importance, needs-reply, risk checks, auto follow-up on sent mail, agent labels, plain-language rules limited to archive / mark_read / unsubscribe / trash, autonomous below importance 2 (above it `queueForAgent` holds the effect as a pending card, on Free nothing happens) — `isGmailEffect`, enforced by `createRule` / `updateRule` in `services/rules.ts`); everything that uses an LLM is Pro (Home/queue, drafts, summaries, autocomplete, Ask AI, commitments, boards, people notes, tasks, Telegram, MCP). Server-side gating: oRPC `agent` middleware on every LLM or agent-only procedure; MCP answers 403 and Telegram replies `proOnly` for Free; the worker skips the morning messages for Free. AI analysis only looks at the last 3 days (`ANALYZE_WINDOW_DAYS`), so an upgrade never pays for the backlog; the one exception is a board's bounded history (cheap model, entries only). The web reads `me.plan` (`useHasAgent`); a Pro entry point stays visible on Free and goes through `useWithAgent(feature, action)` (`components/upgrade-dialog.tsx`), which on Free opens `UpgradeDialog` instead (`upgradeStore`; texts in `t.upgrade`); Pro routes' `beforeLoad` sets the store (not on preload) and redirects to `/mail`. Surfaces that only show agent output (summaries, the person panel, settings rows) stay hidden. |
| Billing | Stripe like Tamery but lean (`services/billing.ts`): Checkout for a chosen plan and interval (`STRIPE_PRO_MONTHLY_PRICE_ID`, `STRIPE_PRO_YEARLY_PRICE_ID`, `STRIPE_MAX_MONTHLY_PRICE_ID`, `STRIPE_MAX_YEARLY_PRICE_ID`; success returns to `/settings?upgraded=<plan>`, no Stripe trial — ours is card-free), Billing Portal (cancel and switching plans or intervals — all four prices must be enabled in the portal's Stripe configuration), and one webhook `POST /stripe/webhook` that upserts `subscriptions` by `stripe_subscription_id` for `customer.subscription.created|updated|deleted` — it stores the subscription as `subscriptions.retrieve` returns it now (Stripe does not order events), answers 400 to a bad signature and calls `announceChange`. A subscriber asking for Checkout gets the portal instead; `customerFor` keeps one Stripe customer per user even when two requests race. `userId` travels in subscription metadata. |
| Sending | Everything leaves through the **outbox** (`services/outbox.ts`): manual mail, approved drafts (web, Telegram, MCP) and scheduled mail. A row waits `UNDO_SEND_SECONDS` (or until its `sendAt`), an in-process timer dispatches it exactly and the worker sweep catches restarts; dispatch claims the row atomically (`scheduled → sending`) so Undo and sending never both win. A send Gmail refuses becomes `failed`; when the refusal is the daily sending limit (a rate-limit error whose "Retry after" is more than a minute away, `GmailError.blockedUntil`, never retried in `lib/gmail.ts`) the mailbox gets `sendBlockedUntil` and the notice bar says when sending works again (an approved action goes back to the queue; the user's own mail is listed among the Drafts as "Not sent" and opening it takes it back into the editor through `cancelMail`); a row left in `sending` for 10 minutes (crash mid-send) is marked `failed` by the sweep, never sent again, because Gmail may already have sent it. Undo (`cancelMail`, also for `failed` rows) returns the draft to the editor, or an approved action back to the queue; once sent it throws `AlreadySentError` (oRPC `CONFLICT`, `t.errors.alreadySent`). After sending, the outbox only records the user's own "remind me" choice — sync's `watchSentMail` handles every sent message, including mail sent from Gmail. Mail is multipart (text + HTML from the Tiptap editor). **Saved drafts** (`services/drafts.ts`) are Gmail drafts read live (`listDrafts` per mailbox, the reply target found by thread), never stored; a Gmail draft id belongs to one mailbox, so `saveDraft` recreates it when "From" changes (create first, then delete the old one), Bcc round-trips, and `scheduleMail` deletes the `draft` it was sent from once queued (a failed delete never fails the send). |
| Schedules | `services/schedules.ts`: a **schedule** is an instruction (encrypted), a 5-field `cron` read in the user's current timezone (at most hourly, `nextRunAt`) and a `when` in words for the UI. Created only by the agent (`create_schedule`, consent) from chat or MCP; Settings lists and deletes them. The worker claims due ones with `runningSince` (a claim older than 15 min was cut off by a deploy or crash and runs again) and moves `nextRunAt` only when a run ends. A run sends the instruction through `streamChat` into the schedule's own `chatId` (counts as a message against the plan) and delivers the answer as a push, to Telegram and to WhatsApp with a link to that chat. A failed run posts a note into the chat (`postToChat`) and is delivered the same way; three failures in a row (`failures`) delete the schedule with a note; a used-up message limit skips runs until the month resets, with one note; a plan without the agent skips them silently, counting no failure. Sends and Gmail changes the run asks for wait there as approvals like any chat; while the chat's last turn still waits for one, `askAgent` adds no turn (that would decline it) and the run delivers `schedule.awaitsAnswer` instead. Run logic lives in `worker.ts` because chat → agent tools → schedules would be a cycle. |
| Calendar | `lib/calendar.ts` (plain REST on the mailbox's `primary` calendar, same `GmailAccount` tokens) + `services/calendar.ts`: events are read live per mailbox for the visible range (`singleEvents`, so a recurring event's instances edit one at a time) and never stored; the API caches each mailbox and range in memory for 60 s and drops the user's cache on any create, update or delete through `services/calendar.ts` (changes made in Google Calendar show within a minute). Times travel as Google's own strings — `yyyy-MM-dd` with an exclusive end for all-day events, an ISO date-time otherwise — and the web parses them with `parseISO`. Both scopes are asked at sign-in and when adding a mailbox (an added mailbox whose consent lacks either is refused), so there is no separate calendar connect step. Google's consent screen still lets the user untick one at sign-in (`hasSignInScope` asks Google's `tokeninfo` about the current access token, cached per token, because Better Auth never rewrites `accounts.scope` on a later sign-in; when Google cannot be asked the scope counts as granted): without Calendar, `listEvents` marks that calendar `connected: false` and skips Google, writes throw `CalendarAccessError` (oRPC `PRECONDITION_FAILED`, `t.errors.calendarAccess`), and the notice bar offers Allow access, which runs Google sign-in again; `listMailboxes` marks a mailbox whose sync error is a revoked or narrowed grant `hasLostAccess`, which the notice bar turns into Sign in again or Reconnect; without Gmail, `me.hasGmail` is false (`me.hasCalendar` likewise reports Calendar) and `/_app` sends the user to `/login?missing=gmail`. The scope must be on the Google Cloud consent screen and the Calendar API enabled. |
| Reminders | `reminders` holds snoozes (Gmail INBOX removed, restored with UNREAD when due, canceled instead if a non-own message arrived since the snooze) and follow-ups (due unless a non-own message arrived in the thread since `since`).
