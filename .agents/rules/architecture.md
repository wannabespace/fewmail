# Architecture

| Topic | Rule |
| --- | --- |
| Layout | `apps/api` (Bun + Hono), `apps/web` (Vite SPA, React 19, TanStack Router + Query), `packages/db` (Drizzle + Postgres), `packages/shared` (enums and helpers shared by both), `packages/ui` (the kit). |
| Services | `apps/api/services/*` own all behaviour and take `userId` first. `orpc/router.ts` (web), `mcp.ts` (MCP over Streamable HTTP, API-key auth), `telegram.ts` (grammY) and `whatsapp.ts` (Cloud API over plain `fetch`) only adapt them. Errors a user can cause throw `NotFoundError`, mapped per surface. |
| API layer | oRPC with arktype input schemas. The web imports the `Router` type from `@fewmail/api/router`; outputs typed via `RouterOutputs`. The API package uses relative imports (no `~/` alias) because the web type-checks it. |
| Auth | Better Auth, Google only, with the `gmail.modify` scope, `accessType: offline` and `prompt: consent` (no refresh token otherwise). OAuth tokens are encrypted by Better Auth. Gmail access tokens come from `auth.api.getAccessToken` with the user's Google account row id. **Added mailboxes** (`services/mailboxes.ts`, Settings → Mailboxes) consent through our own Google OAuth (`mailboxConsentUrl`, callback `GET /mailboxes/callback`, redirect URI registered in Google Cloud), never Better Auth's `linkSocial`: their grant lives on the `mailboxes` row (`googleAccountId` searchable, `refreshToken` encrypted) and never becomes an `accounts` row, because Google sign-in finds the user by account and whoever owns an added mailbox would be signed in to this user. The callback requires the browser's own session to match the consent's user, so a consent link sent to someone else adds nothing. Removing one does not revoke the grant (it is shared with that account's own Fewmail, if any). |
| Gmail | Plain REST in `lib/gmail.ts` (no googleapis SDK); every call takes a `GmailAccount` (a mailbox row: no `refreshToken` = the sign-in mailbox through Better Auth). A user has one sign-in mailbox (`googleAccountId` null, created by `ensureMailbox`) plus any added ones; everything above the mailbox (Today, queue, rules, brief) is per user and merges them. Thread changes go to the thread's mailbox (`mailboxOfThread`), replies and forwards leave from the original's mailbox, new mail from `mailboxId` or the sign-in one (`outbox.mailboxId`), search asks every mailbox (`searchMailboxes`). Sync: first run takes `in:inbox newer_than:3d` (60) plus recent sent mail for voice; later runs use the History API from `mailboxes.historyId`, falling back to a full first run when history expired (404). `syncMailbox` claims the mailbox atomically (`mailboxes.syncStartedAt`, taken over after 15 min) because the API and the worker both sync; `lastSyncedAt` is written only after `processIncoming`, so `null` means the first read is still running (Today shows it). Pro: each **board** reads its history once (`readBoardHistory`, `boards.historyReadAt`): up to 300 messages matching its Gmail query from the last 6 months, stored as messages and passed only to `collectEntries` — never to `processIncoming`, so rules, spam and zombies never act on old mail and no Today card comes from it. Search goes through Gmail's own search (`q`), since subjects and bodies are encrypted in our DB. |
| Worker | Separate process and Railway service (`worker.ts`; `pnpm dev` runs it as `dev:worker`), one tick a minute: sync mailboxes older than 2 minutes (and create the mailbox for anyone with settings but none), write due briefs (and send them to Telegram and WhatsApp), push importance-3 actions to both and to devices once (`actions.notifiedAt`), turn due commitments into actions (`processDueCommitments`), run due schedules (`runDueSchedules`), offer the weekly cleanup (`offerCleanup`). A per-key in-memory lock prevents overlap, which is why the worker runs as exactly one replica (see `monorepo.md` → Deploy); the API may scale. The API still dispatches its own outbox timers for exact Undo Send timing; the worker's sweep is the safety net and the atomic claim keeps them from both sending. Telegram and WhatsApp: the API owns the webhooks / polling, the worker only sends. |
| AI | Per email, **Jev** (TypeSafe, `lib/jev.ts`, `services/classify.ts`) makes every typed decision in one call — category, importance score, needs-reply, suggested action, matching rule — and the LLM only writes text (summary, reason, button label, extracted facts) for mail that is not noise; without `TYPESAFE_API_KEY` the LLM does both. `services/agent.ts` `analyze`: Free gets Jev-only analysis (summary = snippet, no LLM); Pro/trial also get LLM text. OpenRouter through the AI SDK (`lib/ai.ts`): `models.fast` (Claude Haiku, Gemini Flash fallback) analyses every message with structured output; `models.writer` (Claude Sonnet) writes drafts and briefs. Prompts never let the model invent facts; drafts contain no placeholders. |
| Database | Drizzle (`packages/db`), uuid v7 ids, `snake_case` tables, **No user data in clear text** (`packages/db/utils.ts`, AES-GCM, `ENCRYPTION_SECRET`): `encryptedText` / `encryptedJson` (random IV) for anything only read back; `searchableText` / `searchableTextArray` (deterministic, HMAC-derived IV) only for columns used in `eq`, `inArray`, `arrayContains`, unique indexes or `groupBy` — addresses, `messages.fromDomain`, Telegram chat ids, WhatsApp phone numbers, Google account ids. Encrypted columns cannot be sorted, `LIKE`d or `split_part`ed in SQL: sort in JS, add a searchable column for the part you need, and give aggregates `.mapWith(column)` so they decrypt. Plain columns hold only ids, dates, flags, enums, amounts, Gmail ids/labels, keyed hashes and public lists. Any new text column from a user or their mail is encrypted. Agent tables (`commitments`, `people`, `boards`, `board_entries`, `tasks`, `unsubscribes`, `bulk_prints`, `domain_sightings`, `payment_details`) live in `packages/db/schema/insight.ts`. Migrations: `pnpm db:generate` then `pnpm db:migrate`. |
| Integrations | Telegram: deep link `t.me/<bot>?start=<linkCode>` links a chat; inline buttons approve/skip/redraft; webhook when `TELEGRAM_WEBHOOK_SECRET` is set, long polling otherwise. MCP: per-user API keys (`fm_…`, stored as sha256), tools mirror the services; `approve_action` sends mail, so its description tells the client to confirm with the user; `handle_thread`, `get_person`, `list_boards` / `get_board` mirror tasks, people and boards. Telegram also takes free text and voice messages (`services/instructions.ts` `followMessage`): the fast model reads each as a reply to draft, a question answered by `askMail`, or neither (the bot answers with what it can do, as do `/help` and `/start` once linked); audio goes to Mistral `voxtral-mini-latest` for transcription and is not stored; replying to a bot message targets its thread. The webhook uses `onTimeout: 'return'`: drafts outlast grammY's 10 s, and a timed-out update makes Telegram retry it and hold every later one. Handler errors reply `somethingWrong` instead of going silent. WhatsApp (`whatsapp.ts`, Cloud API): the settings link opens `wa.me/<WHATSAPP_NUMBER>` with a prefilled `Fewmail <linkCode>` that links the sender's phone; `GET /whatsapp` answers Meta's verify-token check, `POST /whatsapp` checks `X-Hub-Signature-256` with `WHATSAPP_APP_SECRET`, answers 200 at once and handles messages after (Meta redelivers, so seen message ids are skipped). Same commands as Telegram as reply buttons (max 3, titles ≤ 20 chars, body ≤ 1024 — longer text goes first as its own message); free text and voice notes go through the same `followMessage`, replying to a bot message targets its draft. Meta allows free-form messages only within 24 h of the user's last message (`whatsapp_links.lastInboundAt`); outside it the brief and urgent pushes go out as the approved `WHATSAPP_TEMPLATE` (one body variable with a one-line preview, one Quick Reply button whose payload `brief` / `queue` sends the full content once tapped). |
| Notifications | `services/notifications.ts`: `notify(userId, notification)` buffers per user and delivers after `BATCH_MS` (10 s) — whatever arrives in that window goes out as one combined notification. In-memory, so it runs in the worker only and the worker flushes it on SIGTERM. Targets are `devices` (one row per browser / app, `kind` from `DEVICE_KINDS`, `token` searchable, `keys` encrypted); each kind has its own sender — `web` is Web Push (`web-push`, VAPID keys `VAPID_PUBLIC_KEY` / `VAPID_PRIVATE_KEY`, 404/410 deletes the row). Mobile and desktop apps join as a new kind plus a sender, nothing else changes. Web: `public/sw.js` shows the push and opens its `url`; `lib/push.ts` registers it, Settings → Notifications toggles it on every plan, sign-out removes it. Payloads are end-to-end encrypted to the browser, but they carry sender, subject and summary — the privacy policy says so. |
| Client state | TanStack Query via `orpc.*.queryOptions()`; optimistic removal from the queue on approve/skip. No global stores. |
| i18n | `packages/shared/i18n`: `locales.ts` (supported `LOCALES`, `matchLocale`, typed `plural` whose forms are `(n) => string`, and `Rich<Slot>` for messages with nodes inside such as links), `messages/en.ts` is the source of truth and `Messages = typeof en`; every other locale is `: Messages`, so a missing or mistyped key fails the type check. **No string placeholders**: anything with a parameter is a function, anything with a link or node is `Rich`. Adding a string means adding it to every locale in the same task. Web: `useT()`, `useDates()`, `localeStore` (`apps/web/src/lib/i18n.ts`); API/Telegram: `messages[settings.language]`. Right-to-left languages are not supported yet (layout uses physical `ml-`/`pl-`). |
| Marketing & SEO | Public site under `routes/_site*` (`SiteHeader`/`SiteFooter`, `components/site.tsx`; demos in `components/landing-demos.tsx`): `/` landing, `/pricing`, `/compare` and `/compare/$slug`. Content is **English only** (like the legal documents, outside `useT`) and lives in `apps/web/src/lib/marketing.ts` (`PLANS`, `FAQ`, `COMPARISONS` — competitor facts only from their public pages, with `COMPARISONS_CHECKED_AT`). `/` sends a returning user to `/today` from `signedInStore` (localStorage, set by `/_app`'s `beforeLoad`, cleared on sign-out), so the landing never waits on the API. `apps/web/src/lib/seo.ts` `PUBLIC_PAGES` is built from that data; the `fewmail-seo` plugin in `vite.config.ts` derives `robots.txt`, `sitemap.xml`, `site.webmanifest`, shared OG tags and one `<path>/index.html` per public page (`/` is `index.html` itself). The `noindex` app shell is `app.html`; `apps/web/Caddyfile` serves it for every path without its own `index.html`. A new public page is one entry in `PUBLIC_PAGES`; a new comparison is one entry in `COMPARISONS`. |
| Legal & account | `/privacy` and `/terms` are public routes rendering `apps/web/src/legal/*.md`; they describe exactly what the code does (Google API Limited Use included) — a change in what data is read, stored, sent or to whom updates them and `LEGAL_UPDATED_AT` in the same task. Account deletion is Better Auth `deleteUser`: it revokes the Google grant first, then every table cascades from `users`. |
| Plans | `services/plan.ts`: `getPlanInfo` (free / trial / pro / max — an active subscription is Pro when its price is one of Pro's two, Max for any other price, which keeps the old $15 price on Max — else `trial_ends_at`), `hasAgent`. **Usage**: `usage` (one row per user and UTC month) against `PLAN_LIMITS` (`packages/shared/agent.ts`). `analyzePending` takes an `emailAllowance` and the LLM writes only while it lasts (urgent mail +10%), otherwise the email is analysed as on Free; `spendMessage` counts and gates `streamChat` (new user turns only, not approval answers), the `ask` procedure and `followMessage` (Telegram, WhatsApp); `requireRoom` caps boards (`createBoard`) and active tasks (`createTask`). Over a limit services throw `LimitReachedError` (`services/limit-error.ts`) → oRPC `TOO_MANY_REQUESTS` with `{ limit, total, resetsAt }`, which the web turns into `t.limits.*` (`limitText` in `lib/orpc.ts`); the bots answer `t.limits.messages`; `me.usage` feeds the Settings meters. Split: every Jev decision is free (classification, importance, needs-reply, risk checks, auto follow-up on sent mail, agent labels, plain-language rules limited to archive / mark_read / unsubscribe / trash and always autonomous — `requireAgentFor` in `orpc/router.ts`); everything that uses an LLM is Pro (Today/brief/queue, drafts, summaries, autocomplete, Ask AI, commitments, boards, people notes, tasks, Telegram, MCP). Server-side gating: oRPC `agent` middleware on every LLM or agent-only procedure; MCP answers 403 and Telegram replies `proOnly` for Free; the worker skips briefs for Free. AI analysis only looks at the last 3 days (`ANALYZE_WINDOW_DAYS`), so an upgrade never pays for the backlog; the one exception is a board's bounded history (cheap model, entries only). The web reads `me.plan` (`useHasAgent`) and removes AI surfaces instead of disabling them. |
| Billing | Stripe like Tamery but lean (`services/billing.ts`): Checkout for a chosen plan and interval (`STRIPE_PRO_MONTHLY_PRICE_ID`, `STRIPE_PRO_YEARLY_PRICE_ID`, `STRIPE_MAX_MONTHLY_PRICE_ID`, `STRIPE_MAX_YEARLY_PRICE_ID`; success returns to `/settings?upgraded=<plan>`, no Stripe trial — ours is card-free), Billing Portal (cancel and switching plans or intervals — all four prices must be enabled in the portal's Stripe configuration), and one webhook `POST /stripe/webhook` that upserts `subscriptions` by `stripe_subscription_id` for `customer.subscription.created|updated|deleted`. `userId` travels in subscription metadata. |
| Sending | Everything leaves through the **outbox** (`services/outbox.ts`): manual mail, approved drafts (web, Telegram, MCP) and scheduled mail. A row waits `UNDO_SEND_SECONDS` (or until its `sendAt`), an in-process timer dispatches it exactly and the worker sweep catches restarts; dispatch claims the row atomically (`scheduled → sending`) so Undo and sending never both win. Undo (`cancelMail`) returns the draft to the editor, or an approved action back to the queue. Mail is multipart (text + HTML from the Tiptap editor). |
| Schedules | `services/schedules.ts`: a **schedule** is an instruction (encrypted), a 5-field `cron` read in the user's current timezone (at most hourly, `nextRunAt`) and a `when` in words for the UI. Created only by the agent (`create_schedule`, consent) from chat or MCP; Settings lists and deletes them. The worker claims a due one by moving `nextRunAt` first, then sends the instruction through `streamChat` into the schedule's own `chatId` (counts as a message against the plan) and pushes the answer linking `/agent?chat=…`. Sends and Gmail changes the run asks for wait there as approvals like any chat. Run logic lives in `worker.ts` because chat → agent tools → schedules would be a cycle. |
| Reminders | `reminders` holds snoozes (Gmail INBOX removed, restored with UNREAD when due) and follow-ups (due unless a non-own message arrived in the thread since `since`). A user-set "remind if no reply" works on Free by resurfacing the thread; on every plan `services/sent-mail.ts` `watchSentMail` detects sent mail that expects an answer (Jev noul) and sets a follow-up (a `follow_up` action on Pro). Pro also extracts promises into `commitments`; `processDueCommitments` turns due ones into `commitment` actions. |
| Live updates | `lib/live.ts`: services call `announceChange(userId)` after anything a user should see without reloading (sync, board history, boards, brief, reminders, commitments, cleanup offer). It is a Postgres `pg_notify` because the worker is another process; only the API `LISTEN`s (`relayChanges` on boot) and fans out through an `@orpc/publisher` `MemoryPublisher` to the `live` procedure, an oRPC event iterator (SSE). The web opens it once in `/_app` (`listenForChanges`), invalidates every query on each event and reconnects after 5 s — no polling. |
| Inbox state | Sync reads Gmail history for new messages **and** label changes, so archive/read/snooze done in other clients shows up — **two-way everywhere**: whatever the user does in Fewmail goes to Gmail (opening a thread marks it read, `markThreadRead`), whatever they do in Gmail comes back. **Gmail push** (`services/gmail-push.ts`): with `GMAIL_PUSH_TOPIC` set the worker keeps a `users.watch` per mailbox (renewed a day before `watchExpiresAt`), Pub/Sub pushes to `POST /gmail/push`, signed with an OIDC token of `GMAIL_PUSH_SERVICE_ACCOUNT` (audience = the endpoint URL, verified with `jose` against Google's keys), which finds mailboxes by `addressHash` (keyed hash; `email` is not searchable) and syncs them at once; the 2-minute poll stays as the safety net; the Important, Needs reply and Quiet filters are slices of the Gmail inbox, and unread counts (`countUnread`) count only unread inbox mail; `changeThreadLabels` (`services/thread-labels.ts`) changes Gmail and mirrors locally at once. Mail actions work on whole threads. |
| Composer | `apps/web/src/components/composer` (Tiptap v3, pinned): bubble menu, `;` snippets, ghost-text autocomplete (`mail.complete`: Mistral Codestral FIM, chat-model fallback), Mod-Enter / Escape ladder handled inside the editor. HTML ↔ text helpers live in `@fewmail/shared/email` for both web and API. |
| Agent tools & chat | `services/agent-tools.ts` `agentTools(userId)` is the one list of what the agent can do (name, description, zod input, `access`: `read` / `write` / `consent`); `mcp.ts` registers it (consent → `destructiveHint`) and `services/chat.ts` turns it into AI SDK tools where `consent` means `needsApproval`. A new capability is one entry there and reaches both. Agent mode (`chats.send`) streams `streamText` (writer model) as UI-message chunks through an oRPC event iterator (`streamToEventIterator` / `eventIteratorToUnproxiedDataStream` in the web's `useChat` transport). The client sends only its last message; history lives in `chats.messages` (encrypted) and is merged by message id, so a regenerate drops what followed and an approval answer replaces its assistant turn. An approval left unanswered when the user writes again counts as declined. |
| Ask AI | `services/ask.ts`: `toGmailQuery` turns plain language into a Gmail search with the fast model (text already holding operators like `from:` passes as typed); every mail search — the Mail field, ⌘K, MCP `list_mail` — goes through it. The writer answers from the found mail with `[n]` citations shown as sources in ⌘K. |
| Spam shield | `services/spam.ts`, on every plan. Sync order (`processIncoming`): `assessRisks` → `measureBulk` → `catchZombies` → `applySpamShield` → `applySimpleRules` → `analyzePending` → `watchSentMail` → (Pro) `advanceTasksFor`. `sender_reports` keeps one vote per user and sender as **HMAC hashes** (keyed with `BETTER_AUTH_SECRET`; rotating it resets reputation) — never addresses or content. Your own vote applies to you at once; community spam needs ≥ 3 distinct reporters (≥ 5 for a company domain; freemail domains never count) and a Laplace-smoothed spam share ≥ 0.8, so one user can never flag a sender for others and not-spam votes pull it back. People you have written to are never moved by community votes. **Patterns, not addresses** (`services/patterns.ts`): every spam / not-spam vote also lands on the message's text fingerprint (`template_reports`, simhash bands, ≥ 3 reporters), its sending network (`pattern_reports` kind `infra`: keyed hash of the /24 or /48 that handed the mail to `mx.google.com`, ≥ 5 reporters at ≥ 0.9, applied only to a first-seen domain or mail without DMARC pass — shared ESP networks carry honest mail) and its unfamiliar link domains (kind `link`, popular domains excluded, ≥ 3). Gmail's own `Authentication-Results` (`lib/mail-auth.ts`, only the `mx.google.com` header is trusted) → `messages.auth`; DMARC fail with neither SPF nor DKIM passing is spam, DMARC fail on a known domain is a `spoofed_sender` risk. Weak signals score one point each — odd domain shape (letters/digits flipping or no vowels; TLDs where the spam feed outnumbers popular sites ≥ 100×, country TLDs only with zero popular sites), a domain registered < 30 days ago (RDAP, cached in `domain_ages`, first-seen domains only) and DMARC + SPF both not passing: 1 point → `messages.suspicion` ("Looks like spam", importance ≤ 1, never moved), ≥ `SUSPICION_SPAM` (2) → spam. Pattern checks skip contacts, senders you voted on and anyone vouched not-spam. Moves are `spam` actions (`auto_done`), reviewable in the Spam tab and the handled summary. The privacy policy describes exactly this — keep them in sync. |
| Network signals | Same keyed-HMAC rule as spam: only hashes are shared between users, never content. `services/bulk.ts`: simhash prints in `bulk_prints` with hashed user ids set `messages.bulkCount` (≥ `BULK_THRESHOLD` in `packages/shared/agent.ts` = bulk). `services/zombies.ts`: `unsubscribes` records each unsubscribe; mail from that sender more than 14 days later goes to spam, and the network zombie share feeds the same decision. `services/risk.ts`: lookalike domains (confusable skeleton vs brands and network-popular domains from `domain_sightings`) and changed payment details (hashes in `payment_details`, never clear text) set `messages.risk` and a `security` action. `services/known-domains.ts`: `known_domains` is seeded from public feeds, never from users — `popular` (Majestic top 10k, lookalike targets; same name in another TLD is not flagged), `phishing` (Phishing.Database; sender, reply-to and link domains → `known_phishing` risk), `spam` (StopForumSpam toxic domains → spam shield, unless anyone voted not-spam or you wrote to them), `disposable` (throwaway senders asking for money → `new_sender_payment`). The worker refreshes stale lists (checked hourly); `pnpm --filter @fewmail/api seed:domains` loads all of them now. Licenses need attribution — it lives in the privacy policy. |
| Agent services (Pro) | `services/people.ts`: `people` with an encrypted note, refreshed weekly. `services/boards.ts`: **boards** — `planBoard` (writer model, once per create or new description) turns the user's name + description into a Gmail query and charts (`BoardChart`: type bar / line / area / pie × measure sum / count × groupBy month / week / group / status); new mail reaches a board when its query, narrowed to the analysis window, returns the message, and `extractEntry` (fast model) decides `belongs` and writes the entry (title, group, status, amount, date) in the user's language, reusing the board's known groups and statuses. Charts are computed in `getBoard` (sums use the dominant currency only); the user edits them, the agent never touches them after creation. Everyone with the agent gets a starter **Money** board once (`mailboxes.boardsSeededAt`, worker). `services/cleanup.ts`: weekly Sunday `cleanup` action, `runCleanup` applies it. `services/tasks.ts`: `tasks` ("Handle this") with autonomy `ask` / `auto`, at most `MAX_EMAILS_PER_TASK` sent per task, advanced on new mail in the thread. |
| Batching | `services/batching.ts` + `listQueueWithLater` (`services/mail.ts`): Today cards surface at the brief hour and 7 h later; `security`, `commitment`, task actions and importance ≥ 3 bypass. No user setting; Gmail untouched. |
